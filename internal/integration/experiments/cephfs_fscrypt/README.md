# CephFS fscrypt encrypted directories per client path

Owner: CephFS. Kind: cross-build characterization of client capability.
Test: `TestCephFSFscrypt` (subtests `kernel` and `fuse`), optional batch
`cephfs_fscrypt`.

## Use case and native contract

A SUT that stores data in a CephFS directory protected with fscrypt (per
directory encryption of contents, file names and symlink targets) sets the
policy and holds the key itself; the fixture only prepares a cluster, a
filesystem, CephX identities and client containers in which a test can do
that. This case records which client paths can do it on each supported
build and what a client without the key sees.

The test talks to the clients through the Linux fscrypt ioctls directly
(`FS_IOC_GET_ENCRYPTION_POLICY_EX`, `FS_IOC_SET_ENCRYPTION_POLICY`,
`FS_IOC_ADD_ENCRYPTION_KEY`, `FS_IOC_GET_ENCRYPTION_KEY_STATUS`,
`FS_IOC_REMOVE_ENCRYPTION_KEY`) from Python in the client container, so no
fscrypt CLI is needed. The policy is a real v2 policy (AES-256-XTS contents,
AES-256-CTS names, 32-byte name padding) with a random 64-byte master key
generated by the test and passed on standard input; no dummy-encryption mount
option or `client_fscrypt_dummy_encryption` is used.

| Client path | 19.2.5 | 20.2.4 | 21.2.0 |
| --- | --- | --- | --- |
| Kernel client, Linux 6.8.0 (Ubuntu 24.04), AES CephX keys | works | works | works |
| `ceph-fuse` of the official image | refused: `ENOTTY` | refused: `ENOTTY` | works with MDS caps `allow *` |

- **Kernel client.** The kernel's ceph module implements the fscrypt ioctls.
  It decodes only AES (type 1) CephX keys and tickets, so the case starts the
  cluster with `ceph.WithAuth(ceph.AuthConfig{KeyType: ceph.CipherAES})`:
  20.2.4 and later default to `aes256k`, and the kernel then refuses the
  mount (`libceph: Failed to parse secret: -524`, `mount(2)` returns errno
  524). It needs no `p` MDS flag: it sets the policy under its exclusive auth
  caps and flushes it with them.
- **ceph-fuse before 21.2.0.** The client does not ask libfuse for directory
  ioctls, so libfuse answers any ioctl on a directory with `ENOTTY`
  ([20.2.4 init](https://github.com/ceph/ceph/blob/v20.2.4/src/client/fuse_ll.cc#L1294)),
  and its ioctl handler knows only `CEPH_IOC_GET_LAYOUT`
  ([20.2.4](https://github.com/ceph/ceph/blob/v20.2.4/src/client/fuse_ll.cc#L925),
  [19.2.5](https://github.com/ceph/ceph/blob/v19.2.5/src/client/fuse_ll.cc#L922)).
  libcephfs of both releases has no fscrypt key or policy API, and the client
  refuses write caps on fscrypt inodes with `EROFS`
  ([20.2.4](https://github.com/ceph/ceph/blob/v20.2.4/src/client/Client.cc#L3885),
  [19.2.5](https://github.com/ceph/ceph/blob/v19.2.5/src/client/Client.cc#L3861)).
  Installing an fscrypt tool cannot change that.
- **ceph-fuse 21.2.0.** The client asks for directory ioctls
  ([init](https://github.com/ceph/ceph/blob/v21.2.0/src/client/fuse_ll.cc#L1478))
  and handles the fscrypt ioctls
  ([handler](https://github.com/ceph/ceph/blob/v21.2.0/src/client/fuse_ll.cc#L964)).
  FUSE forwards only `_IOC_SIZE(cmd)` bytes, so the probe uses the fixed-size
  request numbers that handler accepts (`FS_IOC_SET_ENCRYPTION_POLICY` with a
  24-byte v2 policy, a 32-byte `FS_IOC_GET_ENCRYPTION_POLICY_EX` and
  `FS_IOC_ADD_ENCRYPTION_KEY` with a 64-byte raw key). The client writes the
  `ceph.fscrypt.file` field with a setattr request, and the MDS answers a
  setattr that changes an fscrypt field with `EACCES` unless the session's
  MDS caps are `allow *`
  ([MDS](https://github.com/ceph/ceph/blob/v21.2.0/src/mds/Server.cc#L5643));
  `allow rws` and `allow rwps` are refused.

## Requirements

- One cluster: 1 MON, 1 MGR, 1 OSD, filesystem `tc-cephfs` with one MDS, all
  CephX keys AES. Image roles `essential`, `client` and `cephfs`, all of one
  release. The kernel client containers run the client role image (Python 3
  only, no `mount.ceph`); the `ceph-fuse` containers run the official
  `quay.io/ceph/ceph:v<release>` image, because the role images do not ship
  `ceph-fuse`.
- The client containers get `CAP_SYS_ADMIN` and `apparmor=unconfined`, and
  the `ceph-fuse` ones `/dev/fuse`. The cluster's daemons and admin container
  keep their defaults.
- A rootful Linux Docker Engine. For the kernel subtest, the engine's kernel
  must have the ceph filesystem type registered already (`ceph` in
  `/proc/filesystems`, for example after `modprobe ceph` on the host). The
  test never loads a module: it reads `/proc/filesystems` before any
  `mount(2)`, because a mount of an unregistered type would make the host
  kernel load it.
- The test bounds itself to 25 minutes; the batch timeout is 30 minutes.

## Tier and triggers

Optional: no required CI environment is proven to give client containers
`CAP_SYS_ADMIN` and an unconfined profile or to have the kernel module
registered. One run takes about 50 seconds on a Linux amd64 Docker Engine
host with warm images (46 s on 20.2.4, 51 s on 19.2.5, 55 s on 21.2.0).

- Pull request: not in the default checks; a maintainer runs it on the
  head with `/ci run cephfs_fscrypt [on squid|umbrella]`.
- Periodic: never.


Each subtest logs one `FSCRYPT_RECEIPT` line, or `FSCRYPT_CLIENT_REFUSED`
for a client build without fscrypt.

## Admission, observations and controls

Each subtest first runs an admission in the client container that changes
nothing: the kernel release, `ceph` and `fuse` in `/proc/filesystems`,
`/usr/bin/ceph-fuse`, `/dev/fuse`, `CAP_SYS_ADMIN` in the effective set and
the security label. An unprivileged container of the same image must be
refused there (the negative control of the gate). A mount refused with
`EPERM`, `EACCES` or `ENODEV`, or an identity whose key is not AES on the
kernel path, is a missing prerequisite. Then `FS_IOC_GET_ENCRYPTION_POLICY_EX`
on a new, empty directory decides whether the client implements fscrypt:
`ENODATA` means it does; `ENOTTY`, `EOPNOTSUPP`, `EINVAL` or `ENOSYS` means it
does not. Any other answer is a failed supported operation.

With a working client, through two client containers `a` and `b`, each with
its own CephX identity and its own mount:

- **Policy and key.** `a` adds the key, sets the policy on an empty
  directory and reads it back; `b` reads the same policy. Both clients also
  accepted, from root in the client container, a policy naming a key that was
  never added (errno 0): the kernel lets a caller with `CAP_FOWNER` do that,
  and `ceph-fuse` does not check. On the qualified client cohorts the test requires errno 0.
- **Keyed view.** `a` reads two files byte for byte, a symlink target and a
  subdirectory under their plaintext names.
- **Locked view.** `b` has no key (`a`'s key is absent in `b`'s key status,
  so the two mounts do not share a key context). It lists four encoded names,
  gets `ENOKEY` opening each file and `ENOENT` looking up each plaintext name.
  With a wrong key of its own added, the view stays the same. A control
  directory beside it is plaintext through `b`.
- **Exposed metadata.** By inode, `b` sees the same mode, mtime and file
  sizes as `a`. Through the kernel, `b` sees a symlink size of 96 for a
  39-byte target; through `ceph-fuse`, the plaintext target length.
- **Stored state.** After an MDS journal flush, the file's first RADOS data
  object holds 8192 bytes without either end of the plaintext, while the
  control file's object holds it exactly; the encrypted directory's object has
  four omap keys without a plaintext name, while the control directory's has
  `<name>_head`.
- **Key removal with an open file.** While `a` keeps one file open, removing
  the key returns the files-busy flag and the key becomes "incompletely
  removed": the open descriptor still reads the plaintext, opening the other
  file gives `ENOKEY`. After the close a second removal leaves the key
  absent, and the plaintext path gives `ENOENT`. Removing a key is therefore
  not a revocation of handles that are already open.
- **Remount.** A fresh mount of `a` is locked until the same key is added
  again, which yields the same key identifier.
- **Snapshot.** A snapshot of the encrypted directory reads the exact bytes
  through `a` with the key; through `b` its contents are locked. Its name is
  encoded for `b` through the kernel and plaintext for `b` through
  `ceph-fuse`.
- **Cleanup.** Both keys are removed (through `ceph-fuse` a key whose inodes
  the client still caches stays incompletely removed until the unmount), both
  mounts are unmounted, the MDS has no session of either identity, and the
  client containers are terminated.

## Reading the result

- **Pass:** each subtest established the full contract above, or the
  `ceph-fuse` subtest recorded `FSCRYPT_CLIENT_REFUSED` for a client without
  fscrypt (19.2.5, 20.2.4).
- **Observed change:** the kernel subtest is refused by the policy query, a
  plaintext name or byte reaches `b` or RADOS, or the `ceph-fuse` subtest on
  the pinned official 21.2.0 image on Linux 6.8.0 x86-64 is refused. Other
  FUSE client builds are characterized by their actual policy-query result.
- **Unavailable prerequisite:** the subtest fails with `CephFS fscrypt over
  the <path> client refused: <requirement>`: `kernel ceph filesystem`,
  `ceph-fuse binary`, `/dev/fuse device`, `CAP_SYS_ADMIN`,
  `security profile`, `AES Cephx key` or, on the kernel path,
  `client fscrypt support`.
- **Condition not established:** a mount, seed or snapshot fails with a
  native errno that is none of the above; the failure names the step.

## Cleanup and limits

The test unmounts with `umount2`, waits for `ceph-fuse` to exit and for the
MDS sessions to close, and the harness terminates the cluster. Cleanup that
runs after a failure detaches mounts lazily, checks in the client
container's mount table that nothing is mounted below the mount point any
more and fails the test with the failed step otherwise. It waits for
`ceph-fuse` within its own bound and, if the process has not returned,
stops it again once the client container is terminated. The host-side kernel module is
the operator's: the test neither loads nor unloads it.

Not covered: host networking, arm64, Docker Desktop, kernels other than
Linux 6.8.0, mixed client and MDS releases, `noshare` and other kernel mount
options, key sharing between two mounts of one container, v1 policies,
`FSCRYPT_POLICY_FLAG_DIRECT_KEY` or other ciphers, clones of an encrypted
subvolume, and journal recovery of encrypted metadata.
