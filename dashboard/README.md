# Ceph Dashboard

Import `github.com/JSYoo5B/ceph-testcontainers-go/dashboard` to give an
application that consumes the Ceph Dashboard REST API a real Dashboard on a
disposable cluster: an HTTPS listener with the test's own certificate, an
owned account with one role, the endpoint of the active manager after an
authenticated readiness check, and optionally the Object Gateway pages backed
by one owned gateway. Dashboard requests belong to the SUT; the package adds
no Dashboard client and wraps no Dashboard operation. See
[API purpose and purpose tags](../docs/guides/api-purpose.md).

## Order of use

1. **Start a cluster whose managers ship the dashboard module.** The
   essential role image does not; select a manager image that does, such as
   the official image of the same release, with `ceph.ImageSet.MGR` (see
   [Releases and images](../docs/guides/releases-and-images.md)). The other
   daemons keep their role images.
2. **Prepare the Dashboard** with `dashboard.Start(ctx, cluster, cfg)`.
   `cfg.TLS` is the certificate chain and RSA key the listener presents; the
   test keeps the CA. The module's certificate check rejects other key types,
   such as ECDSA, and the listener then never serves, so `Start` refuses them. `cfg.Role` selects the account's role (`read-only` by
   default) and `cfg.Username` its name (generated by default).
3. **Hand it to the SUT**: `Endpoint` returns the active manager's HTTPS URL
   once that manager answered the owned account, and `Credentials` returns the
   account's name and password. The SUT verifies the certificate with the
   test's CA and the name in the certificate.
4. **Meet a failover**: after `ceph mgr fail` or a manager loss, call
   `Endpoint` again. It waits until the new active manager answers.
5. **Add the Object Gateway** when the SUT uses the Dashboard's RGW pages:
   `d.AddGateway(ctx, gateway)` with an owned gateway from `rgw.Start` or
   `rgw.Gateways`. `GatewayLink.Check` asks the Dashboard for the gateway and
   the link's own RGW user; create the SUT's users and buckets with the
   [rgw package](../rgw/README.md) and the S3 client under test.
6. **Clean up**: `d.Restore(ctx)` removes the gateway link, deletes the
   account and puts the module and its options back, or terminate the
   cluster.

```golang
images := ceph.ImageSet{Essential: essential, Client: client, MGR: "quay.io/ceph/ceph:v20.2.4"}
cluster, err := ceph.Run(ctx, "", ceph.WithImageOptions(ceph.ImageOptions{}.WithImageSet(images)),
	ceph.WithClusterConfig(ceph.ClusterConfig{}.WithManagerCount(2)))
testcontainers.CleanupContainer(t, cluster)
if err != nil {
	t.Fatal(err)
}
d, err := dashboard.Start(ctx, cluster, dashboard.Config{TLS: dashboard.TLSConfig{CertificatePEM: cert, PrivateKeyPEM: key}})
if d != nil {
	t.Cleanup(func() { _ = d.Restore(context.Background()) })
}
if err != nil {
	t.Fatal(err)
}
endpoint, err := d.Endpoint(ctx)
if err != nil {
	t.Fatal(err)
}
username, password := d.Credentials()
// Give the SUT endpoint, username, password and the CA of cert.
```

## Concepts and limits

- **Readiness.** `Start` and `Endpoint` pass only when the listener the MGR
  map advertises presents the installed certificate, refuses the account with
  a wrong password, accepts its password, and answers `GET /api/summary` with
  the session token from the manager that the MGR map names active. Every
  connection of the check compares the presented certificate with the
  installed one before it sends a password or the session token, so a stale
  or foreign listener receives neither, and the check sends nothing more after
  a mismatch. An open
  port, an enabled module or a module that can run is not readiness. The
  check runs from the control container. Each check sends one wrong password
  and then the right one, which resets the module's failed-login counter, so
  repeated checks never lock the account.
- **Endpoints.** In bridge mode the listener is the manager's address on the
  cluster network, port 8443: containers on that network reach it, the
  managers publish no host port. In a host-network cluster each manager
  present at `Start` gets a free host port on the public address, so the test
  process reaches the listener; a manager added later uses port 8443. The
  ports are reserved and released just before the module binds them, so
  another process can take one in between; `Start` then fails its readiness
  check.
  A failover changes the URL; there is no invariant URL. A standby answers
  every request with `303 See Other` to the active manager's root URL.
- **Sessions.** A session token is signed with the module's key, which all
  managers share: a token issued by one manager is accepted by the next
  active one. At every login the module records the account and its session
  token in the `mgr/dashboard/MULTICLUSTER_CONFIG` manager option, in plain
  text in `ceph config dump`; do not log that output. The fixture's password
  and the tokens of its readiness checks are masked in diagnostics reports.
- **Ownership.** The module's enabled state and the host-mode listener
  options are held through `override` handles, so a second `Start` or an
  `override.SetMGRModule` of the module is refused while a Dashboard is
  active. The certificate and key are the module's cluster-wide config-keys;
  `Restore` puts back what was stored before `Start` only when they still
  hold the installed certificate, and refuses an outside edit, as the
  override handles do for the module and options. An existing account of the
  same name is refused, never adopted, and no role is created.
- **Restoration.** `Restore` runs every step, returns the joined errors of
  the refused ones and retries them on the next call; it does not disable the
  module while the account or certificate could not be restored, because the
  Dashboard commands need it. The module keeps its access database and token
  signing key (`mgr/dashboard/accessdb_v2`, `mgr/dashboard/jwt_secret`) after
  `Restore`; they hold no fixture account.
- **Object Gateway.** The Dashboard finds its gateway in the service map, so
  `AddGateway` needs the gateway to be the cluster's only RGW daemon. The
  Dashboard connects to the first frontend port the gateway advertises, its
  plain-HTTP listener, which a gateway with `rgw.TLSConfig` serves too; the
  Dashboard's `RGW_API_SSL_VERIFY` option is not involved and stays as it is.
  The link creates its own RGW
  user with `GatewayAdminCaps` (`users=read;buckets=read;metadata=read`, the
  least that lists users and buckets) and stores its key in the cluster-wide
  `RGW_API_ACCESS_KEY` and `RGW_API_SECRET_KEY` manager options, so every
  manager uses it after a failover. `GatewayLink.Remove` puts the prior values
  back only while the options still hold the link's key, and refuses an
  outside edit. The options are plain text in `ceph config dump`; the key is
  masked in diagnostics reports. It never uses the SUT's credentials or
  `ceph dashboard set-rgw-credentials`, which creates a system user. Pages
  that change RGW state are refused by RGW with this identity.
- **Backend failures.** `Check` fails when the Dashboard's answer is empty or
  does not name the gateway and the link's user. With the Dashboard itself
  ready, an identity the gateway refuses (suspended, wrong key) is
  `ErrGatewayRefused` and an unreachable gateway is `ErrGatewayUnreachable`;
  a stopped gateway makes Dashboard RGW requests hang until the probe's time
  runs out, while login and `Endpoint` keep working.
- Out of scope: Dashboard SSO, Grafana, Prometheus and Alertmanager pages,
  orchestrator-backed pages, multisite RGW and multi-cluster management.
